# Migration Guide

This guide helps teams migrate from the v1 transaction confirmation pattern to the TX State Machine. The new approach is simpler, more reliable, and handles edge cases automatically.

## What's Changing

### Old Pattern (v1)

In v1, frontends had to manage the full confirmation lifecycle:

```typescript
// OLD PATTERN - Don't do this anymore

// 1. Build and submit transaction
const txHash = await wallet.submitTx(signedTx);

// 2. Manually poll the blockchain
const pollBlockchain = async (hash: string): Promise<void> => {
  const confirmed = await checkBlockfrost(hash);
  if (!confirmed) {
    await sleep(10000);
    return pollBlockchain(hash);
  }
};
await pollBlockchain(txHash);

// 3. Call a separate confirmation endpoint
await fetch('/course/teacher/module/confirm-tx', {
  method: 'POST',
  headers: { 'Authorization': `Bearer ${jwt}` },
  body: JSON.stringify({
    tx_hash: txHash,
    course_id: courseId,
    modules: moduleData
  })
});

// 4. Handle errors, retries, timeouts manually...
```

### New Pattern (TX State Machine)

Now the Gateway handles everything after registration:

```typescript
// NEW PATTERN - Do this instead

// 1. Build and submit transaction (same as before)
const txHash = await wallet.submitTx(signedTx);

// 2. Register with Gateway (one API call)
await fetch('/api/v2/tx/register', {
  method: 'POST',
  headers: {
    'X-API-Key': API_KEY,
    'Authorization': `Bearer ${jwt}`
  },
  body: JSON.stringify({
    tx_hash: txHash,
    tx_type: 'modules_manage'
  })
});

// 3. (Optional) Poll status for UI feedback
// Gateway handles blockchain polling and DB updates automatically
```

## Deprecated Endpoints

<Callout type="warn">
These endpoints should no longer be called. The TX State Machine replaces their functionality.
</Callout>

| Deprecated Endpoint | Replacement |
|---------------------|-------------|
| `POST /course/teacher/module/confirm-tx` | `POST /api/v2/tx/register` with `tx_type: 'modules_manage'` |
| `POST /course/student/assignment/confirm-tx` | `POST /api/v2/tx/register` with `tx_type: 'assignment_submit'` |
| `POST /course/teacher/assessment/confirm-tx` | `POST /api/v2/tx/register` with `tx_type: 'assessment_assess'` |
| `POST /*/set-pending-tx` | `POST /api/v2/tx/register` |
| `POST /*/sync` | Automatic via TX State Machine |
| Any `/confirm-tx` endpoint | `POST /api/v2/tx/register` |

## Step-by-Step Migration

### Step 1: Identify Current Transaction Flows

Find all places in your codebase where you:
- Call `/confirm-tx` endpoints
- Call `/set-pending-tx` endpoints
- Call `/sync` endpoints
- Manually poll Blockfrost/Koios/Andamioscan for confirmation

### Step 2: Map to Transaction Types

For each transaction flow, identify the correct `tx_type`:

| Your Current Flow | TX Type |
|-------------------|---------|
| Creating a course | `course_create` |
| Student enrolling | `course_enroll` |
| Adding/managing modules | `modules_manage` |
| Updating teachers | `teachers_update` |
| Submitting assignment | `assignment_submit` |
| Assessing submission | `assessment_assess` |
| Claiming credential | `credential_claim` |
| Creating project | `project_create` |
| Joining project task | `project_join` |
| Managing tasks | `tasks_manage` |
| Submitting task work | `task_submit` |
| Assessing task | `task_assess` |

### Step 3: Update Each Flow

Replace the old confirmation logic:

<Callout type="info">
**Before:**
```typescript
await pollBlockchain(txHash);
await fetch('/course/teacher/module/confirm-tx', { ... });
```

**After:**
```typescript
await fetch('/api/v2/tx/register', {
  method: 'POST',
  headers: { 'X-API-Key': API_KEY, 'Authorization': `Bearer ${jwt}` },
  body: JSON.stringify({ tx_hash: txHash, tx_type: 'modules_manage' })
});
```
</Callout>

### Step 4: Update UI Feedback (Optional)

If you want to show confirmation progress to users:

```typescript
// After registering, optionally poll for status
const checkStatus = async () => {
  const { state } = await fetch(`/api/v2/tx/status/${txHash}`, {
    headers: { 'X-API-Key': API_KEY, 'Authorization': `Bearer ${jwt}` }
  }).then(r => r.json());

  if (state === 'updated') {
    toast.success('Transaction confirmed!');
  } else if (state === 'pending' || state === 'confirmed') {
    setTimeout(checkStatus, 10000);
  } else {
    toast.error('Transaction failed');
  }
};

// Start polling after typical block time
setTimeout(checkStatus, 30000);
```

### Step 5: Remove Dead Code

Delete:
- Blockchain polling functions
- Confirm endpoint calls
- Set-pending-tx calls
- Sync endpoint calls
- Manual retry logic for confirmations

### Step 6: Test Each Flow

For each migrated transaction type:
1. Complete the transaction in your app
2. Verify registration succeeds (HTTP 200)
3. Check that database updates automatically
4. Verify UI reflects the new state

## Migration Checklist

Use this checklist for each transaction type in your app:

- [ ] Identified all confirm/sync/set-pending calls
- [ ] Mapped to correct `tx_type`
- [ ] Updated to use `/api/v2/tx/register`
- [ ] Removed manual blockchain polling
- [ ] Removed legacy confirm endpoint calls
- [ ] Added optional status polling for UI (if needed)
- [ ] Tested end-to-end flow
- [ ] Cleaned up dead code

## Common Migration Issues

### Issue: Transaction type not recognized

```json
{ "error": "invalid tx_type" }
```

**Solution**: Check the valid types at `GET /api/v2/tx/types`. Ensure you're using the exact string (e.g., `modules_manage`, not `module_manage`).

### Issue: Auth headers not forwarded

**Solution**: Ensure you're passing both `X-API-Key` and `Authorization: Bearer {jwt}` headers to the register endpoint.

### Issue: Missing metadata for project transactions

Some project transactions require metadata. See [Transaction Types](../transaction-types) for requirements.

### Issue: Still calling old endpoints

If you see 404s or unexpected behavior, search your codebase for:
- `/confirm-tx`
- `/set-pending-tx`
- `/sync`

These should all be removed.

## Need Help?

If you encounter issues during migration:
1. Check the [Transaction Types](../transaction-types) documentation
2. Verify your `tx_type` matches exactly
3. Check the response from `/api/v2/tx/status/{tx_hash}` for error details
4. Contact the API Gateway team for support
